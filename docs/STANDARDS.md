# 开发规范

本文件记录本仓库的工程约定。目标是让**下一个读代码的人**（很可能是几个月后的自己）能快速判断
"这段为什么不能那样改"，而不是靠翻提交历史或聊天记录。

---

## 一、注释：写约束，不写开发过程

### 该写什么

**"为什么不能改成别的写法"**，以及违反后会怎样。判据很简单：

> 删掉这条注释后，一个聪明人会不会用看起来更自然的方式改坏它？

会 → 必须留，而且要把后果写清楚。

```csharp
// ✅ 好：写清约束与后果
// 采样时刻必须只在位置读数"真的变了"时更新。若改用每次轮询都刷新的时间戳，
// 由于轮询间隔只有 233ms，"距上次采样过了多久"永远是 0 → 进度推算失效，
// 表现为进度条只在源上报新位置时才跳一下。
public DateTime PositionSampleTime { get; set; }

// ✅ 好：写清平台事实（这不是我们的选择，是外部行为）
// ⚠️ 本类必须全程 async，不得出现 .GetAwaiter().GetResult() / .Result / .Wait()。
// 把 SMTC 的异步调用同步化会阻塞线程池线程，而主循环节拍依赖线程池 → 主循环停止推进。
```

### 不该写什么

| 不要写 | 为什么 | 改成 |
|---|---|---|
| `2026-10-11 实测发现…` | 日期与"谁发现的"对读代码的人没用 | 直接写行为与后果 |
| `原先xxx，后来改成yyy` | 提交历史里已有；代码里只该有当前约定 | 只写"现在为什么是这样" |
| `本次交付说明`、`本轮`、`收敛到新实现` | 临时叙述，几周后就失效 | 不写；需要背景就进 `docs/` |
| `测试 231 → 233 条` | 数字会过期，且提交信息里已记录 | 不写 || 复述代码在做什么 | 代码本身就是最准的描述 | 只在"看不出意图"时补一句 |

**保留例外**：涉及**外部平台的固定事实**时，日期可以作为出处保留，但要点仍是事实本身：

```csharp
// ✅ 可以：记录可复查的外部依据
// 该重制版的 AppUserModelId 实测形如 Sonic853.TTPlayerRebuild.EDB4BA0433B1AC19，
// 后缀是包标识哈希、会随构建变化 → 因此只匹配前缀，不匹配全串。
```

### 引用文档，而不是在代码里复述事件

需要完整背景（现象、证据、排查过程）时，代码里只留一句指向文档：

```csharp
// 背景与证据见本地档案 INCIDENTS.md
```

## 二、文档放哪

| 文件 | 内容 | 是否入库 |
|---|---|---|
| `README.md` / `README_CN.md` | 面向用户：功能、安装、常见问题 | ✅ |
| `CHANGELOG.md` | 面向用户：每个版本的可见变化 | ✅ |
| `SECURITY.md` | 面向用户：读取范围、网络流量、风险与撤销 | ✅ |
| `INCIDENTS.md` | **事故档案**：现象、证据、根因、处置、遗留 | ❌ 本地保留 |
| `docs/STANDARDS.md` | 本文件 | ✅ |
| `docs/kugou-reverse-notes.md` | 酷狗逆向笔记（只对维护者有意义） | ❌ 本地保留 |
| `ROADMAP.md` | 决策史与待办（含已放弃方案的取舍理由） | ❌ 本地保留 |

**约定**：
- 事故档案**只增不改**：修好之后不要回头修改"当时的结论"，有新结论就在文末追加"后续"一节。
  误报排查里最容易犯的错就是事后把当时正确的推理改写成现在的结论。
- 事故档案与 `ROADMAP.md` 一样**不入库**（见 `.gitignore`）：代码里可以引用 `INCIDENTS.md`，
  但那只是给本机维护者看的指路，别人 clone 不到它是正常的 —— 因此**不要把只有档案里才有的
  关键信息当成代码注释的唯一出处**：读代码的人必须能从注释本身判断"为什么不能那样改"。
- 用户可见的变化进 `CHANGELOG.md`；内部重构、死代码清理、注释整理**不进 CHANGELOG**（那是开发噪音）。

## 三、测试

1. **每个修复都要有能失败的回归测试**，并且提交前**反向验证一次**（临时让修复失效、确认测试变红）。
   没有反向验证过的测试，不能算数——本项目已经出现过"守卫测试写得看似合理、实际抓不到任何东西"。
2. **断言只用被验证过的事实**。不要凭"我以为这段代码会这样"写断言：
   先用独立小程序打印真实输出，再照着写。开发中反复踩到的坑都是这一条。
3. **不依赖环境状态**。测试会读真实的 `config.json`（程序单例在类型初始化时就加载），
   所以不要假设某个开关是开的；断言要么与开关无关，要么显式构造配置对象。
4. **语言敏感**：断言中文界面文案的测试不要放进 `LanguageSensitiveCollection`；
   改为语言无关的断言（断言数字 / 结构），或明确加入该集合串行执行。
5. 测试串行执行（见 `tests/MuSync.Tests/AssemblyInfo.cs`）：有测试会临时改全局语言与配置单例。

## 四、提交与发版

- 提交信息：`类型: 摘要` + 短横线要点（`fix:` / `feat:` / `docs:` / `release:`），要点写**用户或维护者能感知的变化**，不写逐行流水账。
- **推送 main 可以；打 tag、发版、改版本号必须先给用户过目。**
- 发版流程：`MuSync.csproj` 版本号 → `CHANGELOG.md` 把 `[未发布]` 定稿为 `## [x.y.z] - 日期`
  （⚠️ 标题必须带方括号，CI 是用 `awk` 按 `^## \[x.y.z\]` 从 CHANGELOG 抽 Release notes）→ 提交 → 打 tag `vX.Y.Z` → CI 出三产物。

## 五、构建环境注意

- 本机若装了会误判测试程序集的杀软，构建会以
  `无法复制 MuSync.Tests.dll，因为找不到该文件` 的形式失败（详见本地档案 `INCIDENTS.md`）。
- **程序运行时会锁住 `bin\Release\...\MuSync.exe`**，此时构建主项目会报 MSB3027/MSB3021；
  先退出程序再构建，或构建到另一个配置。
- 单测命令：`dotnet test tests\MuSync.Tests\MuSync.Tests.csproj -c Release`；
  发布前的完整验证是 **Release 与 Debug 各跑一遍**。
